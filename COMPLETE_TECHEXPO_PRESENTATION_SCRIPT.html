🏗️ Technical Architecture & Process Flow

How the entire pipeline works behind the scenes:

Pipeline Stage Underlying Technology What Happens in the Background
1. Detection & Ingestion Octokit REST API / Webhooks Listens for workflow_run.completed with conclusion failure. Downloads runner logs via GitHub API.
2. Noise Filtering Regex Heuristic Pre-Processor Strips ANSI colors, runner setup logs, and isolates the specific compiler error (e.g. cannot find symbol, incompatible types).
3. Fast-Inference Reasoning Groq LPU (Qwen 2.5 Coder / Llama 3.3) Runs inference at ~400 tokens/sec. Analyzes AST, diagnoses semantic root cause, and generates surgical replacement code.
4. Ephemeral Sandbox Node.js child_process / Docker Applies candidate patch in isolated memory/disk directory. Executes native toolchain (javac for Java, node --check for JS, py_compile for Python).
5. Reflection Engine Autonomous Feedback Loop If exit code ≠ 0, captures the compiler error and prompts Groq to reflect and fix. Bounded to 3 attempts to prevent loops.
6. Git Dispatcher GitHub Git Data API Fetches base SHA, creates refs/heads/ci-doctor/fix-..., writes blob/tree/commit, and opens a Pull Request against main.
7. CI Verification Intelligent PR-Scoped GitHub Actions GitHub runner triggers on the PR branch, runs git diff against base, verifies that all modified files pass checks, and marks the PR Green ✅.

🎯 Top 10 Tough Judges Q&A Defense

Q1 "What is the use of the 'SYNTHESIZE QA TEST SUITE' button?"
Winning Answer: "Most software repositories — especially algorithmic, legacy, or competitive programming repos like this DSA repo — have zero unit tests. They rely on manual verification, which leads to silent regressions when code changes. The SYNTHESIZE QA TEST SUITE button shifts CI-Doctor from reactive repair to proactive prevention. It scans algorithm functions, analyzes edge cases (zero, negative numbers, integer overflow, empty arrays), and autonomously writes complete, idiomatic test suites (like JUnit or Pytest). This establishes a safety net so bugs are caught before code ever reaches production."
Q2 "How is CI-Doctor different from GitHub Copilot or Cursor?"
Winning Answer: "GitHub Copilot and Cursor are interactive developer tools that require a human sitting in an IDE typing prompts. CI-Doctor is an autonomous backend swarm. It triggers in the background when a CI pipeline fails at 2:00 AM, parses runner logs, compiles the patch in a sandbox, and has a verified, passing Pull Request waiting on GitHub before the developer even opens their laptop."
Q3 "What prevents the AI from hallucinating broken code or breaking production?"
Winning Answer: "Our Sandbox Verification Gate and Branch Isolation. The agent is strictly forbidden from opening a PR unless the patch passes native dry-run compilation (e.g. javac) with Exit Code 0. Furthermore, it never commits to main; it only pushes to an isolated feature branch (ci-doctor/fix-...). Finally, GitHub Actions runs intelligent PR-scoped verification to independently re-verify the patch before any human merges it."
Q4 "Why did you use Groq instead of OpenAI GPT-4?"
Winning Answer: "Latency is the difference between a real-time developer tool and an annoying bottleneck. Traditional cloud LLMs take 30 to 60 seconds just to stream reasoning tokens. Groq's custom Language Processing Unit (LPU) silicon achieves ~400 tokens per second. This allows CI-Doctor to ingest logs, diagnose errors, reflect through a multi-turn compiler loop, and open a PR in under 15 seconds."
Q5 "What if the agent enters an infinite loop trying to fix code?"
Winning Answer: "We enforce two strict bounds: Iteration Bounding (maximum 3 reflection attempts) and Execution Timeouts (maximum 20 seconds per sandbox run). If the code fails compilation after 3 attempts, the agent gracefully aborts, logs the full diagnostic trace to the reasoning console, and alerts the developer without polluting the Git history."
Q6 "How do you stop the AI from cheating by deleting or weakening tests?"
Winning Answer: "We implement Gate 1: The Immutable Test Benchmark Shield. During the self-healing repair phase, any files located in test directories or matching test patterns are marked strictly read-only. The agent's file modification tool only permits edits to implementation source files. If the AI attempts to touch a test file, the tool throws a permission violation and rejects the operation."
Q7 "Is this system polyglot, or does it only work for Java?"
Winning Answer: "CI-Doctor features dynamic language ecosystem detection. When inspecting a repository, it examines file extensions and project manifests. If it detects pom.xml or .java, it deploys Java CI with OpenJDK 17 and javac. If it detects package.json, it uses Node.js and npm test. If it detects requirements.txt or .py, it uses Python with pytest and py_compile."
Q8 "How does the GitHub Actions CI workflow know what files to test in a PR?"
Winning Answer: "We built Intelligent PR-Scoped Verification into the deployed .github/workflows/ci.yml. In a monorepo or large codebase with 40+ algorithm files, compiling every single legacy file during a PR can cause false positives from unrelated legacy files. On Pull Requests, our workflow executes git diff --name-only origin/main to target and strictly verify only the modified files. On the main branch, it runs a full repository scan."
